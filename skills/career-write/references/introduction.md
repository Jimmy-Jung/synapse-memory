# 자기소개: 어떤 문제를 좋아하고 어떻게 일하는 사람인가

작성자: JunyoungJung · 작성일: 2026-09-22

## 구성

정체성 → 이를 뒷받침하는 대표 경험 → 동기와 일하는 태도 → 필요한 경우 방향·개인적인 면모로 연결한다. 문장 수나 취미·유머를 고정 요건으로 만들지 않는다. 채용 자기소개 문항이나 글자 제한이 있으면 그 질문에 직접 답하도록 구성한다.

- 첫 문장에서 직함뿐 아니라 다루는 문제와 관심을 드러낸다. '열정적인 개발자' 같은 자기평가를 기억 가능한 경험과 행동으로 바꾼다.
- 전체 경력을 나열하지 않고 중심 정체성을 설명하는 경험을 고른다. 경험이 주장을 뒷받침하지 못하면 정체성을 더 좁히거나 사용자에게 확인한다.
- 동기·가치관·감정은 사용자가 말했거나 근거 문서에 있는 것만 쓴다. 구현 사실만으로 '오래전부터 교육에 사명감을 느꼈다' 같은 내면을 발명하지 않는다. 해석은 검토 자료에 후보로 남긴다.
- '협업을 중시한다'면 실제 협의·피드백·역할 분담을 보여준다. 자신감과 동료 존중을 함께 유지한다.
- 유머·자기비하·취미는 자연스럽고 실제인 경우에만 쓴다. 원문 저자의 목공이나 거창한 포부를 가져오지 않는다.
- 짧은 소개만으로도 누구인지 알 수 있게 쓰고, 긴 경력·기술 설명은 별도 문단이나 공개 링크로 연결한다. 인사말 유무와 종결어는 게시 위치와 사용자의 말투에 맞춘다.

## 가상 수정 예시

다음은 규칙 설명용이며 사용자의 경력 근거가 아니다.

> 수정 전: 저는 소통 능력이 뛰어나고 혁신을 주도하는 개발자입니다.
>
> 수정 후: 기능을 만들기 전에 실패했을 때의 동작을 함께 정리하는 개발자입니다. 주문 화면을 맡았을 때 서버 개발자와 재시도 조건을 맞추고, 사용자가 다음 행동을 알 수 있도록 오류 안내를 정리했습니다.

수정 후 문장도 실제 그런 일을 했다는 근거가 있을 때만 사용할 수 있다.

## 확인

정체성과 대표 경험이 연결되는지, 동기와 태도를 임의로 만들지 않았는지, 개인 행동과 공동 결과가 구분되는지 확인한다. 불필요한 수식·기술 나열과 억지 친근함을 줄인다.
